# 로드맵 7 — 원작과의 차이 좁히기: 조작감 · 밀도 · 살아 있는 화면

**상태: A 완료(2단 점프) + 에셋 교체 체계 완료 + 원작 스타일 에셋 v4 게시, B~H 대기 — 2026-09-21 작성**

> **[2026-09-21 추기 #1 — 에셋은 (c) 외부 PNG로 결정]** "후자로 할 거야, 에셋은 계속 바꿀 거야, 예시도 만들어 줄 수 있어?"라는 지시로 §12-1은 (c)로 확정. 게임이 캔버스로 그리던 그림 35종에 전부 이름을 달아 등록하고(`spriteTex(w, h, draw, '이름')`), 시작할 때 `web/assets/manifest.json`을 읽어 같은 이름의 PNG가 있으면 그 그림으로 바꿔 끼우게 했습니다(커밋 5045376). 없거나 깨지면 캔버스 그림으로 되돌아가므로 한 장씩 바꿔 가며 확인할 수 있습니다. 예시로 캔버스 그림을 그대로 뽑은 PNG 35장 + `manifest.json` + 규격서 `web/assets/README.md`를 올렸습니다(커밋 052c014). 규격서에는 파일별 픽셀 크기·게임 안 크기·발 자리·시트 칸 순서·타일 규칙·색 표가 있습니다. 그림 판의 가로세로 비율은 코드에 고정이라 비율만 지키면 픽셀 수는 커도 됩니다. B~G가 진행되면서 파일이 늘어나면(나무 윗면 판, 27칸 캐릭터 시트, 슬라임 프레임) 규격서를 그때그때 갱신합니다. §11의 "외부 이미지 에셋 도입 안 함"은 이 추기로 뒤집힙니다 — 단, 외부 **3D 모델**은 여전히 안 들입니다.
>
> **[2026-09-22 추기 #2 — 웹사이트에서 렉: 최적화]** "클로드 안에서는 안 걸리는데 웹사이트에서는 렉이 심하다"는 보고. 원인 후보를 코드에서 찾아 다섯 가지를 고쳤습니다(커밋 83df471). (1) **미니맵이 매 프레임 GPU를 멈춰 세웠다** — 원형 미니맵을 그리려고 렌더 타겟의 픽셀을 CPU로 읽어(`readRenderTargetPixels`, 384×384) 2D 캔버스에 옮기고 있었는데, 이 읽기는 GPU 파이프라인을 매 프레임 완전히 비우는 동기 호출이라 GPU가 좋을수록 오히려 손해가 큽니다. 렌더 타겟 텍스처를 화면 오른쪽 위 원 안에 바로 찍는 GPU 블릿으로 바꾸고(셰이더에서 원 밖은 버림), 갱신도 3프레임에 한 번으로. M 지도만 예전 방식(열려 있는 동안은 게임이 멈춰 있어 괜찮음). (2) **지형 19만 정점을 늘 통째로 그렸다** — 정점 버퍼는 공유한 채 인덱스만 6×8 타일로 나눠 메시 48개로 만들어 화면 밖 타일은 절두체 컬링으로 빠지게(외곽선 hull도 같이). 법선은 나누기 전에 계산해 이음새 없음. 위치에 따라 삼각형 27~60% 감소. (3) **그림자** PCFSoft→PCF, 맵 2048→1536, 갱신 2프레임에 1회(태양이 플레이어를 따라가므로 한 프레임 늦어도 안 보임). (4) **해상도 배율** 상한 2→1.5, 최근 90프레임 평균이 22ms보다 느리면 0.25씩 1.0까지 내리고 12ms보다 빠르면 다시 올림(`?dpr=1`로 고정 가능). 고해상 모니터에서 픽셀 수가 4배였던 것이 가장 흔한 렉 원인. (5) 수면보다 1.2 이상 높은 땅 밑의 물 칸은 만들지 않음. `?debug`에 fps·배율·드로우콜·삼각형 수를 표시합니다. 내장 브라우저(RTX 4070 SUPER, 672×823)에서는 최적화 전에도 92fps였으므로, 사용자 브라우저의 렉이 계속되면 브라우저 하드웨어 가속(chrome://gpu)·전체화면 해상도·다른 탭의 부하를 봐야 합니다.
>
> **[2026-09-22 추기 #3 — 원작 스타일 에셋 v4 게시]** "영상 확인 후 에버플래닛과 똑같은 모델링으로 에셋을 뽑아봐" 지시로, 원작 영상(1:30~3:40)을 확대 캡처해 외형을 다시 확인하고 규격서의 35종을 전부 새로 그려 `web/assets/`에 덮어썼습니다(커밋 f1f2851, `manifest.json` version 4). 두 차례 뽑은 뒤 "나무·돌은 1차, 비행정은 2차, 별은 별 모양으로" 지시대로 종합했습니다. 반영한 원작 특징: 나무는 스캘럽 잎덩이 4겹(위로 갈수록 연두)·세로 잎결·짧은 뿌리 기둥, 비행정은 흰/파랑 길쭉한 선체·나무 갑판·주황 허브에 노란 날개·양옆 파란 엔진 포드(빛나는 구)·옆구리 잎 문양, 텐트는 청록 천막·초록 잎 문양·노란 교차 기둥, 떨어진 별은 별 모양 돌판 위 청록 웅덩이와 떠 있는 청록 5각 별, 캐릭터는 갈색 위로 묶은 포니테일·초록 상의·배낭(2등신에 가깝게 머리 키움), NPC는 은비(주황 머리·파란 모자·제복)/도토(앞치마·붉은 머리띠)/조프(은빛 투구·빨간 깃·창·수염), 슬라임은 파란 물방울에 큰 눈, 갈대는 부들, 아치·선돌은 이끼 낀 사암 블록. 제작 방식은 캔버스 스크립트(공통 색표·스캘럽·잎 도우미)로 그려 Playwright로 2배 해상도 PNG를 뽑고, 투명 배경·발 자리(불투명 최하단을 맨 아래 줄로 자동 보정)·타일 사방 이음새를 스크립트로 검사한 뒤 실제 `evergreen-3d.html`에 끼워 35/35 로드와 화면을 확인했습니다. 게시는 아티팩트 페이지에서 파일을 클립보드로 복사 → GitHub 업로드 페이지 입력칸에 붙여넣기(사용자가 Ctrl+V) → JS로 File 객체 복원·SHA-256 대조 → 업로드 input에 주입하는 경로를 썼습니다. B(밀도)·C(십자 판)는 아직이며, C가 들어가면 `tree_*_top.png`가 추가됩니다.

> **[2026-09-22 추기 #4 — 화질 단계·자동 조절, 브라우저별 렉 진단]** "Edge에서는 플레이할 수 없을 만큼, 크롬에서는 살짝 렉, 클로드 안에서만큼 부드럽지 않다"는 보고. 추기 #2의 자동 조절이 CPU 시간만 재고 있어(GPU가 느린 건 못 잡음) 실제 프레임 간격(rAF)으로 바꾸고, 화질을 3단계로 정리했습니다(커밋 a603c04, b1f530a): 높음(배율 ≤1.5·그림자 1536) / 중간(1.0·1024) / 낮음(0.75·512·미니맵 6프레임마다·그림자 4프레임마다). 자동은 120프레임 중간값이 21ms를 넘으면 한 단계 내리고 9ms 미만이 3구간 연속이면 올립니다(처음 4초는 안 잼). Q 키로 자동→낮음→중간→높음 순환(기억됨), `?q=low|mid|high` 고정, `?fps`로 왼쪽 위에 fps·프레임 ms·화질·해상도·GPU 이름 표시. WebGL 렌더러 이름이 SwiftShader/소프트웨어면 화면 상단에 "하드웨어 가속을 켜라"는 경고를 띄웁니다 — Edge가 "플레이 불가" 수준이면 십중팔구 이 경우(설정 → 시스템 및 성능 → 그래픽 가속 사용) 또는 효율 모드입니다. 내장 브라우저는 창이 작고(672×823) 배율 1이라 픽셀 수가 전체화면 1440p의 1/6, 4K 배율 1.5의 1/20이라서 같은 컴퓨터여도 부드럽게 보입니다. 미니맵 위치 계산(getBoundingClientRect) 캐시, 프레임당 Vector3 할당 제거도 같이. 남은 확인: 사용자 브라우저의 `?fps` 수치(특히 GPU 이름).

로드맵 6으로 렌더러·지형·구조물·HUD·NPC·슬라임·컷신까지 한 바퀴를 돌았습니다. 이제 원작 영상(1:50 착륙 초원, 2:25 야영지, 3:16 슬라임 비탈)을 지금 판과 나란히 놓고 보면 "구조는 같은데 화면이 비어 있고 딱딱하다"는 것이 남은 차이의 핵심입니다. 이번 로드맵은 새 구역을 늘리지 않고 **지금 있는 별내림 천문대를 원작 화면의 밀도와 움직임에 맞추는** 데 씁니다. 첫 번째 지시였던 2단 점프는 작업 A로 먼저 넣어 게시했습니다.

## 2. 작업 A — 조작감 (완료, 커밋 7a5088c)

- **2단 점프.** 땅에서 Space → 1단(초속 8.8, 높이 1.2). 공중에서 Space 한 번 더 → 2단(초속 8.2). 합쳐 최고 약 2.1이라 단구(2.5)는 여전히 계단으로만 오르고, 바위벽(4.5+)은 못 넘습니다. 2단 점프 발치에 흰 고리가 퍼집니다.
- **코요테 시간 0.12초.** 발판 끝을 걸어서 벗어난 직후에도 1단 점프가 됩니다(데크·다리 끝에서 "분명 눌렀는데" 하는 억울함 제거).
- **점프 버퍼 0.12초.** 착지 직전에 누른 Space는 닿는 순간 실행됩니다.
- 대화·인벤토리·컷신 중에는 점프 입력을 받지 않습니다. 물에 빠져 복귀할 때 점프 횟수를 리셋합니다.

검증: 디버그 훅으로 1단 최고 1.17 / 2단 최고 2.08, 착지 후 횟수 0, 콘솔 에러 0.

## 3. 작업 B — 초목 밀도

원작 1:50 프레임을 세어 보면 한 화면(약 40×25 유닛)에 나무 10그루, 덤불 6~8, 꽃 군집 5, 버섯 3~4, 바위 조각 2~3입니다. 우리는 나무 26그루를 구역 전체(약 80×90 유닛)에 뿌렸으니 밀도가 1/4입니다.

- 나무 26 → **90~110그루.** 좌표 직접 배치는 구조물 옆 "얼굴이 되는" 나무 20그루만 남기고, 나머지는 시드 난수 산포로 바꿉니다(로드맵 5 §10 원칙의 예외를 여기서 하나 둡니다 — 나무는 "소품"이 아니라 "지형"에 가깝습니다). 제외 반경: 길 1.6, 구조물 3, 물가 1, NPC·별 2.5.
- 덤불 → 60, 꽃 → 군집 40개(한 군집에 3~7송이), 버섯 → 군집 20개, 바위 조각 → 30. 군집은 중심 하나 + 반경 1.2 안 난수.
- 나무 기둥 충돌은 유지하되(`canStand`), 덤불·꽃·버섯은 통과.
- 성능: 나무 100그루는 각각 판 하나라 드로우콜 100 — `InstancedMesh`로 묶으면 그림 3종 × 1 콜. 텍스처 아틀라스(한 캔버스에 3종)로 만들어 인스턴스마다 UV 오프셋을 attribute로 넘깁니다. 그림자 캐스팅은 인스턴스도 가능(customDepthMaterial).
- 미니맵 점(mapDot)은 나무마다 찍지 말고 인스턴스 하나에 layer 2 판을 함께 둡니다.

## 4. 작업 C — 나무·덤불 입체화

판 하나짜리 나무가 "종이"로 보이는 순간은 두 가지입니다: 캐릭터가 나무 바로 옆을 지날 때(옆에서 보면 두께 0), 그리고 큰 나무가 화면 위쪽에 있을 때(윗면이 없어 납작).

- **십자 판 + 윗면 판.** 나무 하나 = 남향 판(지금 것) + 동향 판(같은 그림, 90° 회전) + 윗면 판(둥근 잎덩이 위에서 본 그림, 지면과 평행하게 캐노피 높이에). 카메라가 북향 고정이라 동향 판은 옆으로 지날 때만 보이고, 윗면 판은 카메라 각도(40°)에서 늘 살짝 보입니다. 세 판 모두 같은 툰 색이라 이음새가 튀지 않습니다.
- **크기 3종.** 큰 나무(높이 7~8, 기둥 굵음, 덩굴 2~3가닥 늘어짐), 보통(5~6), 작은 나무(3.5~4, 잎덩이 2개). 산포 비율 2:5:3.
- **덤불도 십자 판.** 덤불은 윗면 판 없이 십자만.
- 그림 다시 그리기: 잎덩이 5~7개를 겹쳐 그리되, 원작처럼 윗면 하이라이트 넓게·아랫면 그늘 좁게, 덩이 경계에 어두운 잎 결 선. 기둥은 굵기를 1.5배로, 뿌리 쪽이 벌어지게.
- 나무 그림자는 남향 판의 그림 모양대로(지금 방식) 유지.

## 5. 작업 D — 캐릭터·몬스터 애니메이션

- **플레이어 시트 확장.** 지금 6칸(뒤·앞·옆 × 걷기 2) → 뒤·앞·옆 × (대기 2 + 걷기 4 + 점프 1 + 공격 2) = 27칸. 대기는 숨쉬기(어깨 1px 상하), 걷기 4프레임은 팔다리가 교차하는 중간 자세 포함, 점프는 다리를 모으고 팔을 위로, 공격은 팔을 휘두르는 2프레임(첫 프레임에 휘두름 판, 둘째에 원위치).
- **슬라임.** 튀는 2프레임 → 4프레임(눌림·펴짐·공중·착지), 피격 시 흰색 깜박임 3프레임 + 뒤로 0.4 튕김, 소멸 시 4프레임 터짐(방울 6개 흩어짐)과 반투명 링.
- **NPC.** 제자리 숨쉬기 2프레임(1.2초 주기), 말 걸면 고개 끄덕 1프레임.
- 시트가 커지면 텍스처 오프셋 대신 `repeat`+`offset`을 프레임 표로 두고, `charTex.offset`을 프레임 인덱스에서 계산합니다. 그림자용 depth 재질도 같은 오프셋을 따라가야 합니다(지금은 map만 공유하므로 자동).

## 6. 작업 E — UI 채우기

원작 1:50 프레임의 UI 배치는 로드맵 6 E로 맞췄으니, 남은 것은 "빈 칸"입니다.

- **스킬바 아이콘.** 1번 칸 기본 공격(칼 휘두름), 2번 칸 "슬라임 밟기"(작업 F의 스킬 1개), 나머지는 잠금 자물쇠 그림. 쿨타임은 칸 위에 어두운 부채꼴로.
- **상단 퀘스트 목표.** 화면 상단 중앙(지역명 팝업 자리 아래)에 현재 목표 한 줄 + 진행도 "(1/3)" — 원작 3:16 프레임의 위치.
- **키 안내 팝업.** 컷신 끝나고 4초 동안 화면 중앙에 W A S D · Space · Z 키 그림이 든 반투명 박스(원작 1:50). 첫 대화 후에는 안 뜸.
- **데미지 숫자.** 흰색 → 노랑(보통)·주황(2단 점프 중 공격 = 크리티컬 1.5배). 위로 튀며 커졌다 작아지는 곡선.
- **미니맵 테두리.** 지금 얇은 두 줄 → 원작처럼 두꺼운 황갈 나무 테두리 + 모서리 장식 4개, 위에 "N" 대신 작은 나침반 그림.
- **채팅 입력.** Enter로 입력줄 열기, 쓴 글이 로그에 "탐사자: …"로 남음(네트워크 없음).

## 7. 작업 F — 전투 한 단계

로드맵 6 §12에서 미뤘던 "본격 전투"의 첫 단계만 합니다.

- **슬라임 반격.** 플레이어가 1.0 안에 0.8초 머물면 슬라임이 몸통 박치기(HP −8, 뒤로 0.6 밀림, 화면 가장자리 붉은 비네트 0.2초). HP 오브의 숫자와 채움이 줄어듭니다. HP는 5초간 맞지 않으면 초당 2 회복.
- **사망·부활.** HP 0 → 캐릭터가 주저앉는 1프레임 + 화면 어두워짐 2초 → 마지막 안전 지점(`player.safe`)에서 HP 50%로 부활, 로그 한 줄. 페널티 없음.
- **경험치·레벨.** 슬라임 1마리 = 경험치 12, 레벨 1→2에 60, 이후 레벨당 +40. 레벨업 시 캐릭터 발치에 노란 링 + "LEVEL UP!" 글자 + HP 전회복. 레벨은 이름표에 "Lv.2 탐사자".
- **스킬 1개 — 내려찍기(X).** 공중(1단·2단 점프 중)에서 X → 수직 낙하 후 착지 반경 1.8 안 슬라임 전부에 데미지 25, 착지에 흙먼지 링. 쿨타임 4초, MP 10 소모(MP 50, 초당 1 회복). 2단 점프와 짝이 되는 스킬이라 작업 A와 이어집니다.
- 여기까지만: 다른 몬스터·장비·아이템 드롭은 다음 로드맵.

## 10. 작업 순서와 게시 단위

A(완료) → **B+C 함께**(초목 밀도와 입체화는 같은 산포 코드를 건드리므로 한 번에) → D → E → F → G → H

한 번에 게시할 단위: B+C 한 번, D 한 번, E+F 한 번, G 한 번, H. 로드맵 6처럼 "보고 나서 방향 판단"이 필요한 것은 B+C(밀도가 너무 빽빽하면 길이 안 보일 수 있음)이므로, B+C 게시 후 한 번 봐 주시는 것이 좋습니다.

## 12. 결정이 필요한 것

1. **에셋.** "나머지는 에셋 문제"라는 판단이 맞습니다. 선택지는 (a) 이 로드맵처럼 캔버스 그림을 더 잘 그린다, (b) 무료 픽셀/카툰 스프라이트 팩(CC0)을 들여와 판에 붙인다, (c) 직접 그린 PNG를 `web/assets/`에 두고 불러온다. (b)·(c)는 파일 하나짜리 구성이 깨지고 라이선스·저작권 확인이 필요합니다. 기본값은 (a)로 진행하고, (c)를 원하시면 그림 규격(캔버스 크기·투명 배경·발 위치)을 정해 드리겠습니다.
2. **밀도 상한.** B의 나무 100그루가 저사양 노트북에서 60fps가 나오는지는 게시 후 확인이 필요합니다. 안 나오면 인스턴싱 + 그림자 캐스팅을 큰 나무만으로 줄입니다.
3. **전투 난이도.** F의 슬라임 반격 데미지 8·플레이어 HP 100은 "죽기 어렵게"의 값입니다. 더 긴장감을 원하시면 HP 60 / 데미지 12로.
4. **내려찍기 키.** X로 두었지만 Z 옆이라 오타가 날 수 있습니다. Shift나 마우스 오른쪽도 가능합니다.
